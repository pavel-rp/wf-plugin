# /wf:fleet — dependency-ordered fan-out of /wf:ship subagents

`/wf:ship` takes **one** task to a merged pull request. `/wf:fleet` takes **many**: it reads their dependency graph, then keeps a pool of isolated shipper subagents running — each shipping one item via the same build → checks → merge pipeline `/wf:ship` drives — dispatching an item only once every item it depends on has merged, and supervising the whole fleet until the last pull request lands. It is the automation of hand-babysitting a wave of parallel pull requests.

**You are the orchestrator.** You run in the main conversation. You never write task code yourself; you dispatch, observe, unstick, and dispatch the next wave. The shippers do the work in isolated worktrees.

**Goal state (non-negotiable):** every in-scope item is a **merged pull request** (or honestly **blocked** with a stated reason). Do not stop while any item is unmerged and unblocked.

`/wf:fleet` orchestrates only through the abstract **delivery** and **tracker** provider contracts and the runtime Agent tool — it names no concrete version-control, tracker, or review tool, and it runs no raw delivery command of its own.

## Prerequisites

Before the first bundled resolver MCP call in this skill/agent, run `pwd -P` and use the returned absolute current Agent/session workspace directory as `workspaceRoot` in every call. In a linked-worktree Agent, that cwd is the Agent's own worktree; never inherit a parent Agent's root. Pass `workspaceRoot` explicitly on every resolver call; omission is a hard schema error, and the resolver has no default or fallback root.

**Before any other phase**, obtain project config through the bundled resolver's `resolve_config({ workspaceRoot, ... })` query — it returns the workspace root, the registry location, `coreConfig` (including `taskRoot`), and `coreVersion`, already resolved from `_local/config.md` (core performs no direct config-file parse). `{task-root}` below comes from `coreConfig.taskRoot` — never hardcode it. If the resolver reports the project is uninitialized (absent `_local/config.md`), stop and instruct the user to run `/wf:init` first. If the resolver runtime is unavailable, stop and report that it is not loaded (restart Claude Code) — do not hand-parse config as a fallback.

**Hold the resolved version.** `coreVersion` is the declared version of the core plugin **this run is executing**. Keep it as the run-scoped **resolved version**: it is stamped into the scoreboard header at Step 0 — before the first dispatch — and rendered in the terminal block. It rides the call just made; never issue a second resolver call for it. A `null` value renders the literal token `unknown` at both sites, and the run continues normally: a version that cannot be resolved never blocks a run, and is never guessed, defaulted, or inferred from an install path or a timestamp. It is the left-hand side of the currency check below — the one comparison it enters into; a `null` value gives that check nothing to compare and it says so.

**Require a delivery provider.** Resolve the `delivery` surface once via `resolve_provider({ workspaceRoot, surface: "delivery" })` and hold the run-scoped record. `/wf:fleet` has **nothing to merge** without a delivery provider, so a missing one is a hard stop:

- The delivery surface is **unconfigured** (no capability owns it) → **`FLEET — Blocked`**: "No delivery provider is registered — nothing to open or merge." Dispatch no shipper, merge nothing. Stop.
- A registered delivery capability is **unrecoverable** → **`FLEET — Blocked`**, naming the record's diagnostics as a hedged candidate. Stop.
- Otherwise hold the record for the delivery reads below.

**Check the running version against the newest published one.** Run this **once per run**, here at Prerequisites — never per item — on the `delivery` record just resolved, and **before the hard stop above emits its block**, so a run with nothing owning the surface still reports a currency outcome instead of nothing. Branch on **surface ownership** — the record's `state` — never on what a read returned:

- **Owned** — invoke the delivery `newest-published-version-read` operation **once** (obtain its body via `resolve_content({ workspaceRoot, ... })`, `class: fragment`, from the record just held), passing `coreConfig.versionDeclaration` as the already-resolved `<version-declaration>` and leaving `<version-field>` to the owner's default. When that config value is `null` there is nothing to ask for — skip the read entirely.
- **Unowned** — no published state is reachable, so fall back to the **local install inventory** the resolver already serves read-only (`discover_packs`): take the newest version it records for the unit the running version belongs to — the entry carrying that version — and `none recorded` when no entry carries it. This query is paid **only** on this branch.

Then render exactly one **currency outcome**. There are four leading tokens and **only `current` asserts currency**, emitted **only** on `<read-performed>` = true:

- `current — running <version>, newest published <version>` — the read was performed and the running version is not behind. No warning.
- `trailing — running <version>, newest published <version>` — the read was performed and the running version is behind. **Warn here, at Prerequisites**, naming both versions — before the scoreboard is written and before the first dispatch. The warning **informs**: it never gates, aborts, or updates anything.
- `provider-less — no delivery provider; newest recorded locally <version | none recorded>` — the surface is unowned, so the check never reached a published state at all. This is **not** a pass and never renders as one. Warn in the same place, with the same shape, when the locally recorded version is ahead of the running one — stating that the comparison was against the local inventory, not a published state.
- `not checked — <reason>` — the check did not complete. `<reason>` is the read's own closed-set token (`read-failed`, `none-published`) verbatim, or one of core's two: `no version declaration configured`, `running version unknown`.

The check runs on **every** invocation, so the `Currency:` slot always renders one of these and never a blank. A resumed run re-checks and reports what it observes now; the scoreboard's stamp records what the run began on, and neither is corrected against the other.

**A tracker is optional.** Resolve the `tracker` surface via `resolve_provider({ workspaceRoot, surface: "tracker" })`. When one is registered, umbrella expansion and blocking-edge reads are available. When none is (the surface is unconfigured), `/wf:fleet` runs **tracker-free**: it accepts only an explicit id list plus `--after` edges, does no umbrella expansion and reads no tracker edges, and surfaces no tracker-derived term. This branch is decided **only** by whether the tracker surface is owned — never by naming a provider.

**Obtain the composed constitution — carry it to every shipper.** The plugin's SessionStart hook injects the project's composed constitution into a normal session's context, but that hook does **not** fire in an Agent-tool worktree shipper session (determined empirically, WF-335): a dispatched worktree shipper is a nested subagent context, not a top-level Claude Code session, so no SessionStart event fires for it and its fresh worktree carries none of the `_local/` snapshot the hook would build. The unattended shippers are the very sessions that most need the non-negotiable rules, so `/wf:fleet` carries the constitution to them explicitly. Read the composed constitution **once** from `_local/constitution.md` — the same fingerprinted source the hook emits, so there is no second composition path — and hold it as the run-scoped **constitution payload**. If that file is absent or empty (no `/wf:constitution` has run), hold no payload and carry nothing downstream — mirroring the hook, which injects nothing when there is no constitution record.

## Command Syntax

```
/wf:fleet <id> [<id> …]              explicit item list
/wf:fleet <umbrella-id>              a tracker umbrella — ship all its children (tracker mode only)
/wf:fleet                            resume: re-read the scoreboard and continue
```

### Arguments

| Argument | Required | Meaning |
| --- | --- | --- |
| `<ids>` / `<umbrella-id>` | on first launch | The items to ship. An umbrella expands to its children via the tracker; expansion needs a registered tracker. |
| `--model <name>` | NO | Pin one model for **all** shipper subagents (`sonnet`, `opus`, …). **Default: omit → the resolver's static top-tier shipper default, stepped down one tier once only if the host lacks it (see Model selection).** Use `--model sonnet` when low on tokens. Does not change the orchestrator's own model. |
| `--max-parallel <N>` | NO | Positive integer cap on concurrently-running shippers, validated before graph dispatch and bounded by the core maximum of 4. Default 4. Lower it if the machine or rate limits strain; values above 4 still resolve to 4 and zero/negative/non-integer values hard-stop. |
| `--after "<id>:<blocker>,<blocker>; …"` | NO | Extra dependency edges beyond the tracker graph — use to encode **same-file contention** (below) the tracker doesn't record. Always available, tracker or not. |

### Zero-argument default

Invoked with no arguments, `/wf:fleet` **resumes**: it re-reads the scoreboard at `_local/fleet/scoreboard.md`, reconstructs the graph, every durable routing-ledger record, and every `dispatched`, `in-flight`, and `awaiting-confirmation` activation from it, and continues the tick loop. Resume the exact persisted boundary with the retained operation: a persisted decision with no spawn continues that decision's spawn; a persisted terminal outcome and complete evaluation with no `postAttempt` response submits `postAttempt` against the retained prior; a persisted retry disposition with no replacement spawn launches only its recorded `retry.unitIds`. Never issue a fresh initial `resolve_routing` call for those attempts, never reset the retry cap, and preserve the recorded attempt, basis, selector provenance, and escalation origin across `/clear`. Reconcile each persisted activation intent deterministically before computing readiness. A `dispatched` row always carries the durable activation-intent token written before spawn: if authoritative runtime state correlates that token to an active agent, persist its `agentId`, worktree, and branch and mark it `in-flight`; if it proves the activation terminated or never existed, return it to `queued`; if no `agentId` was persisted and live-or-terminal state cannot be established, mark it `awaiting-confirmation`, keep it occupying capacity, and continue token-correlated supervision. Never infer absence from a missing `agentId`, requeue an uncorrelated intent, or duplicate-launch it. If the runtime cannot correlate the token, require explicit manual safety confirmation before terminally blocking or requeueing the item. `awaiting-confirmation` cannot substitute for a missing routing-ledger record; a missing or malformed retained record hard-stops recovery rather than silently rerouting. If no scoreboard exists, stop and ask for an explicit item set: `/wf:fleet <ids-or-umbrella>`.

## Step 0 — Build the graph and the scoreboard (once, at first launch)

1. **Resolve the item set.** Explicit ids → that set. An umbrella id (tracker mode) → its children via the tracker `list_children` operation. Record each item's id and title. **Refuse any id that is not a single safe path segment** — empty, containing `/` or `\`, equal to `.` or `..`, or carrying a control character — before any path is built from it: record its row `blocked` with `blocked: unsafe item id — <which rule it failed>` and never dispatch it. The id is refused, never sanitized into a different one, because it names the item's lens exchange folder and task folder verbatim.
2. **Read the dependency graph.** In tracker mode, read each item's blocking predecessors via the tracker `list_blockers` operation. An edge `A blocked-by B` means **do not dispatch A until B is merged**. Merge in any `--after` edges. Tracker-free, the graph is exactly the `--after` edges. Items with no unmet blockers are the initial **ready set**.
3. **Validate acyclic, then order by dependency.** Topologically order the items; if the graph has a cycle or an edge to an unknown id, **stop and report it** before dispatching anything — never guess an order.
4. **⚠ Encode same-file contention as edges.** The tracker records *logical* dependencies, not *file* ones. Two items with no logical dependency that edit the **same file** (a shared contract, a shared agent, a shared config) will collide at merge. Before running, add a blocking edge between them via `--after` so they serialize. Version-manifest files (a shared version file / plugin manifest) are the exception — those collide on **every** parallel merge and are handled by rebase-and-re-bump (merge etiquette), not by serialization. Only serialize on **content** overlap. If you cannot tell, serialize — a wasted wait is cheaper than a lost agent to a conflict.
5. **Write the scoreboard** to `_local/fleet/scoreboard.md` (create `_local/fleet/` if absent). It is the durable state — re-read it every tick so the run survives an interruption or a `/clear`. Stamp it with a `**Model:** <the runtime model id>` line, a `**Version:** <the run-scoped resolved version | unknown>` line recording the harness this run is executing, a `**Currency:** <the currency outcome>` line recording what that version was found to be against the newest published one, a `**Setup command:** <coreConfig.dependencySetupCommand verbatim | none declared>` line echoing the one dependency-setup command every shipper's worktree will run — taken from this run's own Prerequisites `resolve_config` record, never from a shipper's report — an `**Opened:** <UTC ISO-8601 instant>` line opening this run's receipt window, and a stable scoreboard run id. The version and currency stamps are written here, at the scoreboard's first write — **before the first dispatch** — so the record of which harness produced the run exists even if the run is interrupted before any item merges. They record the harness the run **began** on and its currency then, and neither is re-stamped on resume; a resumed run's terminal block reports the version it is executing **now** and the currency it observes **now**, so stamp and block legitimately differ when a run resumes under an upgraded harness. Neither is corrected against the other — each states what it observed. `**Opened:**` is the lower bound of this run's **receipt window**: a receipt is scoped to the task rather than to the run, so this stamp is what gives the proof-of-ceremony check a run scope. It is a UTC ISO-8601 instant taken from the machine clock, in the same shape a receipt's `issuedAt` carries, so the two compare directly as instants — never a local-zone or date-only rendering, which would skew every verdict in one direction. It is written once, at this same first write, and a resumed run reuses it **verbatim** — re-stamping it to the resuming moment would silently discard every receipt the run has already earned. A resumed scoreboard that carries **no** `**Opened:**` stamp, having been written before this stamp existed, is never back-filled and never re-stamped: that run has no receipt window at all, so every item on it resolves `unproven: run window absent` and the `Ceremony:` slot reports explicit zeros. One row per item: `id | title | status (queued|dispatched|in-flight|awaiting-confirmation|awaiting-review|merged|blocked) | blockers | activationIntent | routingAttempt | agentId | worktree | branch | PR | notes`. Before every spawn, derive a canonical activation-intent token from the scoreboard run id, item id, and routing attempt; atomically persist that token with status `dispatched`, then include the same token in the spawn prompt. Only after the spawn returns persist its `agentId`, worktree, and branch and transition to `in-flight`. The pre-spawn write is mandatory: a crash between spawn and response persistence leaves a correlatable, capacity-consuming intent rather than permission to launch a duplicate. `awaiting-confirmation` is nonterminal: it means the activation is preserved while a token-correlated silence probe awaits explicit child/runtime state, occupies an in-flight pool slot, never satisfies a dependency blocker or closeout, and must re-arm supervision. `awaiting-review` is nonterminal in exactly the same way: the shipper has opened its pull request and handed back to wait for a requested review against this orchestrator's deadline (OBSERVE §"Review wait"); it dispatches no child, keeps its pool slot, never satisfies a dependency blocker or closeout, and re-arms supervision. Wherever this skill lists the live activation states — `dispatched`, `in-flight`, `awaiting-confirmation` — `awaiting-review` is one of them. The `notes` cell carries any working-state checkpoint the runtime or child explicitly reports; the orchestrator never manufactures one by probing the worktree. Also record the resolved `--model`, `--max-parallel`, and the mode (tracker or tracker-free).
6. **Write the durable routing ledger** in the same scoreboard, keyed by `routingAttempt`; every activation row references exactly one ledger record. A record persists the full compact routing prior/decision: role, ordered `unitIds`, the bijective canonical token→opaque-item-id map, normalized shape evidence, `executionShape`, `effectiveParallelism`, model and effort selector values with each selector's source, fallback, and masked state, whether the decision **carried** a selection this run had already resolved for that item rather than deriving one at the wave edge, basis, attempt, escalation origin, optional `actualModel` when present, disposition, `retry.unitIds`, retained unit ids, terminal outcome, and the complete ordered evaluation. Use an explicit `—` for fields not yet produced; never discard or reconstruct an earlier value. This ledger, not `awaiting-confirmation`, is the durable routing/recovery state.

**Per-item row convention.** Every item in scope owns exactly one row for the whole run, from the scoreboard's first write to its terminal outcome. **Every per-item state is recorded in that row** — the row is updated in place and never deleted, so a state is never conveyed by an absent or missing row. The `status` cell carries the current state from the enumerated set; **any state other than plain `merged` also carries its reason in `notes`, rendered `<state>: <one-line reason>`** and appended after the existing content rather than overwriting it, so an item's successive reasons stay readable in order. A **halted** item — one whose shipper reported a non-success build outcome instead of a merge — is recorded `blocked` with `blocked: <the exact outcome reported> — <the blocking reason it carried>`, and its `PR` cell stays `—` because no pull request was opened for it. **The `PR` cell follows the pull request, never the status:** it is `—` only while no pull request exists for the item, and a `blocked` item whose pull request is open — a `review not awaited` stop, a lapsed review, red checks — records that pull request there, so closeout and the operator can find it from the row alone. Any further per-item state a later addition records in this row uses the same `<state>: <reason>` rendering in `notes` rather than a second shape.

**The ceremony verdict is one such state.** Every item that reaches a terminal outcome carries exactly one of `proven: <the item's evidence class, assigned by the weighting rule> — <the matched subjects>` or `unproven: <the stated reason>` in its `notes`, in that same rendering, appended rather than overwriting. It is recorded **alongside** the delivery outcome, never instead of it: the `status` cell keeps its enumerated value, so a merged item whose ceremony could not be proven is `merged` in `status` and `unproven: …` in `notes`. An item with no verdict yet simply has no such entry — the row itself is never absent.

### The task-artifact persistence destination

A dispatched shipper builds its item's task folder inside its own isolated worktree, and the task root is untracked, so that folder is the **only copy in existence** — a pruned worktree takes the run's whole process record with it while the work it produced survives elsewhere. This run therefore persists each item's **agent-authored task artifacts** — the markdown a phase writes into the task folder — to a destination of its own: **`{task-root}/<id>/` in this orchestrator's own workspace**, one folder per in-scope item, named by that item's own id — or, for an item whose source was archived, the matching **`{task-root}/_archive/<id>/`** — or, for the attempt-qualified trigger below, **`{task-root}/<id>/attempt-<k>/`**, `<k>` the routing attempt the replacement is entering. That is the entire declaration: no other path is written, and no path outside these three is implied.

The destination answers to the **same write-scope article** as every other write here — it lies **inside the task root**, which is where that article already puts agent-authored artifacts, and which resolves inside `_local/`, so the Forbidden rule against writing outside `_local/` is satisfied rather than excepted. A project whose configured task root resolves outside `_local/` has no persistence destination under that rule, and persistence states that rather than writing anyway. It therefore needs no committed-lifecycle exception, declares no committed artifact class, names no committed-lifecycle path, and adds **no** skill to the write-scope exception list. It is a **sibling** of the machine-emitted run-evidence class under that shared article, never a share of it: run evidence is what the harness emits about itself and only the resolver writes it, whereas these are artifacts an agent authored, and the resolver neither writes nor serves them. Two different kinds of thing, two destinations, deliberately not one policy.

**The orchestrator is the only writer, and that is precisely what keeps the shipper's own rule intact.** A shipper that loses its worktree must stop and report rather than fall back to the shared checkout; that prohibition is load-bearing and is **never** relaxed to make persistence work. The orchestrator already runs in the shared checkout and already writes under the task root, so persistence asks a shipper for nothing and changes nothing it is told.

### The attempt-qualified persistence trigger (`verify-loop-halt` only)

This is a **second, additive** trigger, distinct from — and run in addition to — the terminal-row trigger below: it fires at **Boundary 3** (Supervision playbook §C), **before** a replacement is spawned, for exactly the mapped items whose terminal outcome being replaced is `verify-loop-halt` (the item row's `blocked: verify-loop-halt — <reason>` per the per-item row convention). It runs the **same** locate-then-copy-then-index procedure the terminal-row trigger uses (§"Task-artifact persistence" below — same read-only source rules, same staged-then-moved write, same `index.md` exclusion, same one-index-call-per-artifact), but to the attempt-qualified destination above rather than the un-suffixed one, and it is **not** gated on the item's activation being terminal — a replacement is about to be spawned precisely because the prior activation already ended. Firing is keyed to the **routing attempt** the replacement is entering, not to the item, so a second halt under attempt `k+1` persists again beside attempt `k`'s copy rather than being skipped as already-persisted; record the same three-token outcome (`persisted:` / `not-persisted:` / `no-artifacts:`) in the item's row, attempt-qualified (`persisted (attempt <k>): <destination>`). The replacement's dispatch brief (§"The shipper dispatch template") then names that destination and the item's branch, instructing the replacement to seed its own worktree's task folder from it verbatim before anything else, and drives `/wf:ship <id> --gate extend` in place of the plain `/wf:ship <id>`. Supervision playbook §D reuses this same Boundary-3 mechanism by reference, so the trigger applies there unchanged.

## The tick loop (OBSERVE → DISPATCH → SUPERVISE → REPORT → RE-ARM)

Every tick — whether fired by a subagent completion or a re-invocation — do all five, in order, then re-arm.

### 1. OBSERVE (read-only; never mutate a working tree you don't own)

- Read the scoreboard — the authoritative record of where each agent is and what has merged.
- Read what has merged and what is open since last tick via the delivery `activity-read` operation, and each in-flight item's pull-request and check state via `pr-detect` / `checks-read`.
- For each `dispatched`, `in-flight`, or `awaiting-confirmation` activation, observe its progress through the **runtime Agent tool's own signals**, correlating by `activationIntent` first and `agentId` when persisted: a running background shipper surfaces its activity, and a completed one re-invokes you with its final block. When a runtime signal or child report explicitly identifies uncommitted in-progress edits, record that working-state checkpoint in the row's `notes`; it is active progress, never a stall (the **dirty-status-is-not-a-stall** rule). Do not raw-query or infer a child's dirty state from silence. A new commit or pull-request update since last tick is likewise active progress.
- Trust the runtime's own record of **where each agent is actually working** — an agent's assigned worktree can be lost mid-run and it may re-register elsewhere; the runtime's live agent state, not the originally-assigned path, is authoritative.
- Update the scoreboard with every delta (new merges → `merged`; a shipper reporting a halt instead of a merge → `blocked`, with its stated reason written into that row per the **per-item row convention** — an escalation-class halt (`verify-loop-halt` or a no-progress stop) is recorded the same way but then enters the Supervision playbook's escalation-class rule, and stays final `blocked` only when that gate stops, retains, or returns `exhausted`; new commits/pull requests → notes; each row's `worktree`/`branch`/`PR` fields to their latest observed values, so closeout can list leftovers from the scoreboard alone).
- **Review boundary.** A shipper whose report is `SHIP — Handed-off` with `Built: stopped at review boundary` (or, on the fallback path, `RUN — handed-off`) has reached verify's declared review boundary and ended its turn — it is **neither terminal nor stalled**, and no playbook recycles, probes, or replaces it. This path keeps every lens a **direct** child of this orchestrator, so nothing depends on a nested child's completion notice and no shipper ever waits. The report is only the trigger; the request artifact is the source. For that item, once per hand-back:
  1. **Read the request** — `{task-root}/<id>/04_lens-request.md` under the worktree the item's own row records (the runtime's live worktree when it moved), read-only. Absent, unparseable, carrying a `**Tree:**` that is not one path segment of hexadecimal characters, or a `**Round:**` that is not a run of decimal digits → record `lens-boundary: request unreadable`; an item id that is not a single safe path segment (Step 0) → record `lens-boundary: unsafe item id` and build no exchange path; a `**Workspace:**` that does not resolve to that same worktree → record `lens-boundary: request workspace mismatch` — never dispatch against a root the row does not record. On any of these, skip steps 2–3 (there is no request identity to record under) and in step 4 tell the shipper to re-invoke `/wf:ship <id>` **without** `--review-boundary`, so its verify dispatches and counts its own lenses and the item never re-enters the boundary for that tree.
  For each `## Row`, validate its `**Agent:**` token against this orchestrator's own `resolve_registry` before step 2: only a `subagent:` dispatch of a `verify`/`finding` row is dispatchable, and the role is derived from that token, never from the request heading.
  2. **Dispatch every validated row in one message** — for each `## Row` whose token passed that check (any other is recorded `failed — not a registered lens row`), call `resolve_routing` with `workspaceRoot` (Prerequisites), `role` the row's derived role, `unitIds: [<the row's **Unit:** value>]`, `supportsModelSelector: true`, `supportsEffortSelector: false`, and the lens evidence `{ workSurface: "external-context", atomicity: "atomic", unitCount: 1, unitsIndependent: false, ambiguity: "material", risk: "elevated", toolWork: "material", validation: "judgment", contextIsolation: "required", independentReview: true, returnContract: "judgment", requestedParallelism: 1 }`; on `status: stop`, a `diagnostic`, or a shape other than `isolated`, record that row `failed — routing <reason>` and dispatch nothing for it. Otherwise dispatch it via the Agent tool as this orchestrator's own **foreground** child: `subagent_type` the row's `**Agent:**` token, its fenced prompt verbatim, `model:` only when routing returned one, no worktree isolation. A lens is read-only; it reads the shipper's worktree by the absolute `**Workspace:**` path the prompt names.
  3. **Record** — into `_local/fleet/lenses/<id>/<T>/r<N>/` (`<T>` the request's `**Tree:**`, `<N>` its `**Round:**` — the request identity, so a later round on the same tree records beside, never over, an earlier one). **First apply the canonical-containment check** from the Safety Rules' review-boundary write bullet to the exchange parent, the destination, and each target file — no existing component from `_local/` down to each `<role>.md` and `manifest.md` a symlink (an already-present symlinked target file fails, never followed), both resolved real paths strict descendants of `_local/` inside the workspace root — before writing any file or creating any directory. On failure write **nothing**, record `lens-boundary: unsafe exchange path` in the row's `notes`, and in step 4 tell the shipper to re-invoke `/wf:ship <id>` **without** `--review-boundary`, exactly as step 1 does for an unsafe item id; never repair, remove, or follow the offending link. Otherwise: each child whose final output carries a well-formed `AUDIT-<LENS> — clean|findings` block → `<role>.md` holding that block verbatim, outcome `returned`; any other outcome — an error, a stall the runtime reports as terminal, a missing or malformed block, a refused route — → outcome `failed — <one-line reason>`, no file. Then write `manifest.md` **last**, carrying the request's `**Tree:**` and `**Round:**` verbatim, per `verify-spec`'s `review-boundary.md` shape (obtain it via `resolve_content({ workspaceRoot, ... })`, `class: references-template`, `skill: verify-spec`, `ref: review-boundary.md`). Never apply a rubric yourself, and never re-dispatch a failed row in the same hand-back — the resumed verify names it incomplete, which is the honest outcome.
  4. **Continue the shipper** — one message to the same agent id: "Review-boundary lens blocks are recorded at `_local/fleet/lenses/<id>/<T>/r<N>/` under `<SOURCE-ROOT>`. Re-invoke `/wf:ship <id> --review-boundary <exchange>` now and continue to the merge." Record `lens-boundary: <T> r<N> <returned>/<rows> returned` in the row's `notes`; the row stays `in-flight`. If the runtime cannot continue that agent, the item enters Supervision playbook §C unchanged — the recorded blocks survive for whichever activation re-reaches the boundary with the same tree and round.
- **Review wait.** A shipper whose report is `SHIP — Handed-off` with `Built: awaiting review` has opened its pull request, and its pre-merge review step found the review it requested still outstanding. **This orchestrator owns the wait**, on a wall-clock deadline — a shipper never polls, sleeps, or counts attempts for a review, because a count of polls in one turn spans seconds, not the minutes a reviewer takes. Like the review-boundary hand-back it is **neither terminal nor stalled**, and no playbook recycles, probes, or replaces it. The row's `notes` are the wait's only state, so it survives compaction, a `/clear`, and a resume:
  1. **Decide whether a wait is possible.** Read `coreConfig.reviewWaitMinutes` from the Prerequisites `resolve_config` record — a whole number of minutes; `<none>`, absent, or unparseable is the shipped default **30**. A wait is possible only when that value is above `0` **and** this runtime can wake this orchestrator after a delay by itself — a self-paced re-invocation that outlives the current turn (RE-ARM). **Headless print mode is unsupported for the review wait:** a print-mode session ends when its turn ends and holds no timed wake, so waiting there would either hang or silently lapse. When no wait is possible, set the row `blocked` with `blocked: review not awaited — <wait disabled (Review Wait Minutes 0) | no self-paced wake in this runtime>`, keep the open pull request in its `PR` cell, and continue nothing: the item never merges on an unawaited review, and it is never recorded as a pass.
  2. **Record the deadline once.** When the row carries no `awaiting-review:` token, append `awaiting-review: requested <UTC ISO-8601 instant>, deadline <instant + minutes>` — the requested instant is the moment this orchestrator first observes the hand-back, which is at or after the actual review request and so can only lengthen the wait, never shorten it — and set `status` to `awaiting-review` and the `PR` cell to the open pull request. A later `Built: awaiting review` hand-back for the same item **never** resets or extends that deadline: the first recorded token stands. **A hand-back after the continuation is a lapsed wait:** when the row already carries `review-wait: continued <deadline>` — its one continuation was sent, yet the review is still outstanding past the deadline (for example, a respawned or ceiling-resumed shipper that re-entered its review step without `--review-lapsed`) — do not record a new deadline and do not continue the shipper again; set the row `blocked` with `blocked: review lapsed — still outstanding after the continuation`, keep the open pull request in its `PR` cell, and never merge. Every waiting row therefore reaches either one continuation or a terminal `blocked`, never an indefinite wait.
  3. **Arm one depth-0 wake.** This orchestrator — never a child — arms one self-paced wake for the recorded deadline. A wake armed before a compaction may be lost; nothing depends on it, because the next step is re-derived from the row on every tick.
  4. **Continue once, detect-first.** On **every** tick, for each `awaiting-review` row whose recorded deadline has passed and whose `notes` carry no `review-wait: continued <that deadline>` token: append that token **first**, set `status` back to `in-flight`, then send the same agent id **one** message: "Your review wait's deadline has passed. Re-invoke `/wf:ship <ID> --review-boundary <exchange> --review-lapsed` now and continue to the merge." A duplicated wake finds the token and sends nothing; a dropped wake is caught by the next tick that sees the passed deadline — so each deadline is acted on **exactly once**, and re-armed at most once. A row whose deadline has not yet passed is left alone and its wake stays armed. If the runtime cannot continue that agent, the item enters Supervision playbook §C unchanged.
  5. **What the resumed run does.** The shipper re-enters its review step with `--review-lapsed`: a review that landed during the wait is read and addressed and the item proceeds to merge; a review still outstanding blocks as a lapsed, unknown review (never clean), and the shipper reports it `blocked` with its open pull request.
- **Proof-of-ceremony check.** Run this for **every** item whose row has reached a terminal outcome — `merged` or terminally `blocked` — however that outcome was observed, including a merge seen only through the delivery `activity-read` with no shipper report at all; never gate it on the shipper having reported anything. When a report does arrive, **do not read it for proof**: a reported terminal block is composed by the agent whose compliance it attests to, so its presence is satisfied by typing and proves nothing. Resolve the item's own receipts instead: call the `wf-resolver` `read_family_run_evidence({ workspaceRoot, memberRoot, taskId })` query **once per item, at the point the verdict is computed**, reusing the Prerequisites `workspaceRoot`, passing the worktree path the item's **own row** records as `memberRoot`, and the item's id verbatim as `taskId`. A shipper files its receipts from its own isolated worktree, under that worktree's run identity and issuer binding, so this is the read that can find them; the resolver proves the root is a worktree of this repository's family and judges every record against that worktree's identity. A row that records **no** worktree has no receipts to read: the item is **unproven: no recorded worktree**, and no other root is substituted. A `foreign-root` result is **unproven: foreign root** with the read's `diagnostic`. Otherwise the response is `read_run_evidence`'s shape; apply the match rule:
  - **Only phase receipts under `matched` are candidates.** Consider a record only when it appears under `matched` **and** its `kind` is `phase-receipt`. A `gate-approval` record is never a ceremony subject, however its own subject token reads: a self-approval claims a *gate* and a receipt claims a *phase*, and counting one as the other would readmit exactly the agent-authored evidence this check exists to exclude. A record the resolver could not admit comes back under `unmatched` with its own stated `reason` — record that reason, never count it; a shipper that writes a receipt-shaped file itself lands there. A non-zero `unreadableRecords` is the ledger's own tamper signal: record the count and treat the item as unproven.
  - **Window on `issuedAt`.** A receipt is scoped to the **task**, not the run, and carries no per-run nonce, so a record counts only when its `issuedAt` falls at or after this run's `**Opened:**` stamp — compared as two calendar instants, never as strings. The ledger is append-only, so an earlier record for a subject that also has an in-window one is simply superseded and ignored; being out of window is fatal only when a required subject has **no** in-window record at all, which is recorded as `stale-window`.
  - **The route fixes the required set.** Partition the response's own `receiptBearingPhases` rather than a copy of it: `ship` and `tf` are the two delivery-ceremony subjects, and the remainder are the spine subjects — so an added receipt-bearing phase follows the resolver instead of leaving a stale list here. `tf` is required on every route. `ship` is required when the ceremony route was taken; a matched `tf` with no matched `ship` is the documented fallback route, which drives the pipeline directly and files no `ship` receipt, and is recorded with that stated reason rather than as a missing required subject. The spine requirement is narrowed on the evidence's own shape, never on anything the shipper reports: **every spine subject in window** → the full-chain route; **none in window** → no spine evidence exists at all, which is what a legitimately `lite`-routed item looks like, since that phase is uninstrumented and files none, so the ceremony subjects stand as the item's complete proof set and the absent spine subjects count against nothing. That is **also** exactly what an item that simply never ran those phases looks like, and this check cannot tell the two apart — so such an item is recorded `proven: invocation-only` and flagged for the same follow-up gate pass an unproven item gets, never as a full-chain proof. **Some but not all in window** → the route is not decidable from the evidence, recorded as its own stated reason rather than guessed in either direction.
  - **Weight the two receipt classes apart.** Every matched record carries a resolver-assigned `evidenceClass`. The spine subjects are `artifact-backed` — the resolver digested an artifact of its own accord. The two ceremony subjects are `invocation-only`: they attest only that the resolver was invoked at a completion point, which is strictly weaker than that the ceremony *succeeded*, and they are filed on every terminal rather than only the clean one. Classify each **item** by its strongest in-window evidence — any matched spine subject makes the item `artifact-backed`, a ceremony-only proof set makes it `invocation-only` — so the two tallies are **item** counts that partition the proven total exactly. Always render the split rather than the total alone — collapsing an `invocation-only` item into an undifferentiated `proven` is precisely what hides the weaker claim — and never let an `invocation-only` record satisfy a required spine subject on the full-chain route.
  - **State the residual honestly.** A receipt attests that the recorder ran for that subject inside that window. Nothing in the mechanism binds the recording call to a skill's execution, so a `proven` verdict means exactly that and never "forgery-proof". Report the tally as that claim and no stronger; closing the remaining gap belongs to the recording side, not to this check, and overstating it here would repeat the false assurance this check replaced.
  - **Everything else is unproven.** A read status other than `ok`, a required subject with no in-window `phase-receipt`, a non-zero `unreadableRecords`, an undecidable route, an absent or unparseable `**Opened:**` stamp, a row with no recorded worktree, a `foreign-root` read, a `read_family_run_evidence` query the running resolver does not expose at all, or a non-null `diagnostic` each resolve to **unproven**, carrying the mechanical fact that produced it. The check **fails closed**: an item is proven by evidence alone, never by the absence of a contrary signal.

  Record the verdict in that row's `notes` per the **per-item row convention**, and carry the run's counts into the tick REPORT line. The counts account for **every** terminal item: a terminal row left unevaluated is itself `unproven: not evaluated`, never a silent omission from the tally. **Do not assert the cause** — record the read status, the missing subjects, any `unmatched` reason, and the `unreadableRecords` count, and never claim *why* they are missing. A merge cannot be undone, so this check is preventive (the dispatch prompt makes the ceremony mandatory) and detective (this surfacing): its value is flagging an unproven item so its possibly-skipped gates can be run as a follow-up, and never logging one as a clean run.

- **Task-artifact persistence.** Run this for **every** item whose row has reached a terminal outcome — `merged` or terminally `blocked` — **and whose activation is itself terminal**, meaning no `dispatched`, `in-flight`, or `awaiting-confirmation` activation remains for it. A delivery outcome alone is **not** sufficient: a row turns `merged` from the delivery `activity-read` with no shipper report at all, and capturing then would copy a half-written set and record it as a complete one. An item that is terminal by delivery but whose activation is still live is simply left for a later tick. It carries the item's process record out of the disposable worktree that produced it and into this run's declared destination (§"The task-artifact persistence destination"), so the record outlives the worktree. **Persist an item at most once:** record an **in-progress** marker in the row *before* step 2 writes anything and settle it to the final token in step 4, so an attempt interrupted between the two is recognisable on resume instead of re-running from zero and stacking a second copy; an item whose row already carries either is skipped. **A settled token is final for the run**, including a `not-persisted:` one — the step does not retry, so a transient failure is reported rather than quietly re-attempted and the reported gap is a real one. An item deferred because its activation is still live carries no token yet and is counted **deferred**, never as persisted, failed, or absent.
  1. **Locate the set.** Take the worktree path this item's **own row** records — never a path derived any other way, and never a raw worktree query. A row that records **no** worktree has no set to persist and never had one: record it `no-artifacts:` (step 4) and stop there for that item. Otherwise read that item's task folder **read-only** under the recorded worktree: the live `{task-root}/<id>/`, or the archived `{task-root}/_archive/<id>/` when the item was finalized; prefer the archived one when both are present, since it is the later state. Reading is the only thing done to that worktree — nothing is moved, emptied, removed, or pruned. **Refuse rather than read** a source that, once symbolic links are resolved, lands outside the recorded worktree, or that resolves to this orchestrator's own workspace — the shared-checkout hazard, where source and destination would coincide; each is recorded `not-persisted:` with that reason.
  2. **Write it to the destination.** Write the located set into the **matching** path in this orchestrator's own workspace — an archived source to `{task-root}/_archive/<id>/`, a live one to `{task-root}/<id>/` — so a finalized task is never resurrected as in-flight. Use `<id>` verbatim as a **single path segment**; an id that is not one is refused, never sanitized into one. Write the set to a staging location first and move it into place only once the whole set is written, so a write that fails part-way leaves **no** half-populated folder a later reader would mistake for a complete one. When the destination already exists and is non-empty, write beside it under a distinct sibling and delete neither — a task folder that was already there is never clobbered. Copy the task folder's own **regular files** — its artifacts plus the folder slots the index writer's catalogue names — and follow no symbolic link out of the set; nothing else under the worktree is read or copied, so the set is bounded by the task folder's declared shape rather than by whatever that worktree happens to hold. An item whose archived folder this step has persisted is already finalized by its own shipper, so the orchestrator never invokes the finalize skill for it — a persisted archive is never mistaken for a local finalize marker. **`index.md` is excluded from the write set** — never copied, mirrored, or reconstructed — because it has a sole writer and step 3 is the only way this run reaches it.
  3. **Reach the rows only by invoking the index writer, once per persisted artifact.** For **each** artifact step 2 wrote, invoke `/wf:index <id> <slot> "<summary>"` through the Skill tool, passing the `<slot>` that writer's own slot catalogue maps that artifact's filename to and a one-line `<summary>` describing it. That writer edits **exactly one row** per invocation, so a set of N artifacts takes N invocations: a single invocation would leave every other row reading as absent, which is a **worse** record than the one the worktree held. An artifact the catalogue maps to no slot is recorded under its own filename-derived custom slot, which that writer appends. Because the set is bounded to the task folder's declared shape, this is on the order of a phase's worth of invocations per item, paid **once** at the point that item goes terminal and never per tick. These invocations are the **only** way a row is produced here — the orchestrator authors none, the write set in step 2 contains none, and nothing duplicates a row into the destination. The index writer remains the sole writer of every task's `index.md`, exactly as it is everywhere else in the pipeline.
  4. **State the outcome.** Record exactly one persistence token in that row's `notes` per the **per-item row convention**: `persisted: <the destination folder>` when the whole set landed; `not-persisted: <the mechanical reason>` when it could not — a worktree unreadable or already gone, a refused source, or a write that failed part-way; or `no-artifacts: <the stated reason>` when there was never a set to persist — no worktree was ever recorded for this item, or the row predates this step and carries no persistence state to reconcile — which is **not** a failure and is counted apart from one. **A failure is confined to its own item:** every other terminal item still persists, and a non-zero not-persisted count means the run reports an **incomplete** process record rather than presenting the gap as an item that simply has no artifacts. As with the check above, record the mechanical fact and **do not assert the cause**, and never reach for a path the row did not record.

- **Lens coverage.** Run this for **every** item whose row has reached a terminal outcome **and whose activation is itself terminal** — the same condition as the persistence step above: no `dispatched`, `in-flight`, or `awaiting-confirmation` activation remains for it — so incomplete lens coverage is never silent at the fleet level. A delivery outcome alone is **not** sufficient: a row can turn `merged` while its shipper is still writing `04_verify.md`, and reading then would freeze an early `unknown` or partial count that the read-at-most-once rule below could never correct. An item that is terminal by delivery but whose activation is still live is left for a later tick, carries **no** `lenses:` token yet, and is neither read nor counted until its activation is terminal. Read the `**Lenses:**` header line of the item's own `04_verify.md` — **read-only**, from the task folder under the worktree the item's **own row** records (the archived `{task-root}/_archive/<id>/` preferred over the live `{task-root}/<id>/`, exactly as the persistence step's locate rule), or from this run's persisted copy once the persistence step has written it — and take its value verbatim: `<lc>/<le> completed, <li> inline`, with its ` — incomplete: <role>, …` suffix whenever fewer completed than expected, the count `/wf:verify-spec` computed under its own "Lens count" rule — including the lens blocks this orchestrator recorded at the item's review boundary. **Never read it from the shipper's reported block:** that block is typed by the agent whose run it describes, and the item's own report artifact is the source. **Never write or edit that report:** the orchestrator's only lens-side writes are the blocks it records at the item's review boundary, which the item's own resumed verify validates and counts — a row the report names as not completed stays not completed. When no value can be read, record `unknown — <the mechanical reason>` — no worktree recorded, no `04_verify.md` in the task folder, or a report that carries no `**Lenses:**` line — and do not assert the cause. An item whose project registers no lens contributor reads `0/0 completed, 0 inline`, an explicit zero rather than a missing value. Record the value in that row's `notes` per the **per-item row convention** as `lenses: <value>`, read at most once per item (a row already carrying a `lenses:` token is not re-read), and carry it into the tick REPORT line and the `Lenses:` slot. Reporting only: it never blocks, retries, or re-dispatches an item.

- **Review outcome.** Run this for **every** item whose row has reached a terminal outcome, alongside the checks above, so each item's pre-merge review outcome — including a capped merge's recorded cause — is visible per item on the scoreboard. Take the `Review:` line of the item's `SHIP —` block verbatim — the one-line summary the pre-merge review step recorded, or `ship`'s own `none — no review step ran`. This is the **only** place that summary is recorded (`ship` writes no artifact for it), so unlike the lens count it is necessarily the shipper's own report: record it as reported, never re-derive, reclassify, or judge it here. When no value can be read, record `unknown — <the mechanical reason>` — no shipper report arrived (a merge seen only through the delivery `activity-read`), or the report carries no `Review:` line — and do not assert the cause. Record the value in that row's `notes` per the **per-item row convention** as `review: <value>`, read at most once per item (a row already carrying a `review:` token is not re-read), and carry it into the tick REPORT line. Reporting only: it never blocks, retries, or re-dispatches an item.

### 2. DISPATCH (fill the ready set, respecting deps, contention, and the parallel cap)

- Compute the **full ready frontier** in deterministic dependency/input order: queued items whose blockers are all `merged` and that do not share a serialization edge with a `dispatched`, `in-flight`, or `awaiting-confirmation` item. Take each item's model first — the pinned `--model`, otherwise the item's own resolver decision per §"Model selection", **read back from its scoreboard row when one is already recorded and resolved only on the item's first entry here** — then partition the frontier into stable, model-homogeneous groups without reordering items. The full group is only a candidate set; queued excess is never part of a retained routing decision.
- For each model-homogeneous group while pool slots remain, compute available pool slots after counting every `dispatched`, `in-flight`, and `awaiting-confirmation` activation (all occupy capacity) and take the first `min(group size, available slots, configured pool bound, core execution cap of four)` items as the candidate launch wave. Reuse the Prerequisites `workspaceRoot` and call `resolve_routing` with `workspaceRoot` explicitly for exactly that candidate wave, passing ordered canonical identity tokens derived from the item ids as `unitIds` and retaining a bijective token→item-id map; canonicalize by the invocation-runtime rule, disambiguating any collision with a stable SHA-256 prefix. Before every initial or replacement spawn, validate that each selected canonical token maps to exactly one in-scope item and that no two selected tokens map to the same item; a missing, ambiguous, stale, or duplicate mapping hard-stops that dispatch and blocks the affected item with the mapping diagnostic — never guess or pass the token as a task id. **Mapping invariant:** if token `unit-a1` maps to opaque item id `TASK@42`, spawn `/wf:ship TASK@42`, never `/wf:ship unit-a1`; if that mapping is absent or duplicates another selected token's item, spawn nothing. This decision settles topology only: pass the pin as `invocationModel` when `--model` is set, and otherwise no model channel at all, so it re-resolves the shipper default itself. If the returned `effectiveParallelism` is smaller than the candidate wave, dispatch nothing under that decision: narrow to the exact first `effectiveParallelism` items and call `resolve_routing` once more, reusing the same `workspaceRoot`, with singleton or multi-item evidence and ordered `unitIds` for that exact launch wave. Retain only the final decision whose `unitCount` and `unitIds` equal the canonical tokens mapped to the items actually launched. **Boundary 1 — before spawn:** atomically persist that final full decision/prior and token map in the routing ledger before writing any activation intent or calling the Agent tool. Dispatch every item in that exact wave under that persisted decision and leave all excess ready items outside the decision as `queued` for a later fresh initial routing call. `--max-parallel` is the outer pool cap and no decision's `effectiveParallelism` may be exceeded.
- For each selected item, derive its canonical activation-intent token, atomically persist the row as `dispatched` with that token **before** calling the Agent tool, and include the token in the shipper prompt. Count `dispatched` intents as occupied pool slots immediately. After a successful spawn response, persist `agentId`, worktree, and branch and mark it `in-flight`. If the process stops after spawn but before that second persistence, resume reconciliation must keep the intent nonterminal and capacity-consuming, correlate the token against authoritative runtime state, and never spawn the item again until absence or termination is conclusively proved. Aggregate completions back in the original dependency/input order, not completion order.
- When an item merges, its dependents may become ready — dispatch them next tick (or immediately, same tick, through a fresh routing decision for the new frontier).

### 3. SUPERVISE (unstick anything that isn't moving)

Apply the **supervision playbook** (below) to every `in-flight` or `awaiting-confirmation` agent: recycle a genuine stall, resume an interrupted one, take over a mechanical tail, never touch one that's making progress.

### 4. REPORT

One line: `<merged>/<total> done — merged this tick: … — in-flight: … — awaiting-confirmation: … — dispatched: … — waiting: … — ceremony: <p> proven (<a> artifact-backed, <i> invocation-only) / <u> unproven — persistence: <k> persisted / <n> not-persisted / <x> no-artifacts of <t> terminal — lenses: <id> <lc>/<le> completed, <li> inline[ — incomplete: <role>, …] | <id> unknown — <reason>, … | none — review: <id> <recorded review summary> | <id> unknown — <reason>, … | none`. Note any takeover or recycle. The `lenses:` segment carries each terminal item's lens-coverage value from OBSERVE once it has been read (an item whose activation is still live has no entry yet), in scoreboard order, with `none` the stated fallback while no terminal item has been read. The `review:` segment carries each terminal item's review outcome from OBSERVE — a capped merge's recorded cause included — in scoreboard order, with the same `none` fallback.

**Tick REPORT line slot convention.** This line is a grepped shape that no earlier convention governs, so the rules below are the ones that govern it; a later addition **extends** them rather than redefining them. The line is the leading `<merged>/<total> done` count followed by ` — <label>: <value>` segments, and:

1. **Append at the tail.** A new segment goes after the last existing one. No segment is ever reordered, renamed, or removed, so two independent additions append in merge order and cannot contend for a position.
2. **Every declared segment renders on every tick**, with a **stated fallback token** when it has nothing to report — never an omitted segment, never a blank value. Absence is information, so it is stated rather than conveyed by a missing segment.
3. **One label token per concept**, matching the corresponding `FLEET —` slot's label lower-cased, so a concept stays one grep across both shapes.
4. **No pinned value column.** The line is separator-delimited rather than padded, so a new segment carries no alignment obligation and never reflows the line.

These rules bind every segment added **from this convention onward**. The segments that predate it keep their existing label tokens and their `…` placeholder — rule 1 forbids renaming them, so they are not evidence about how a new segment renders, and a later author follows the rules rather than the older pattern. Rule 3 binds only a segment whose concept has a corresponding `FLEET —` slot; a segment with no counterpart there simply keeps its own token.

This is deliberately weaker than the run-block slot convention the terminal blocks follow — that one pins a column, this one has none to pin — and the two are not interchangeable.

### 5. RE-ARM

If any item is `queued`, `dispatched`, `in-flight`, `awaiting-confirmation`, or `awaiting-review`, keep the loop alive and re-arm supervision; `awaiting-confirmation` and `awaiting-review` always count as live activations and can never satisfy closeout. While any row is `awaiting-review`, keep its deadline wake armed (OBSERVE §"Review wait") — that wake is the only thing that ends the wait when no shipper completes in the meantime. Each finished background shipper re-invokes you the moment it completes — that is the primary wake. When nothing is in flight but work remains (e.g. you just recycled something and want a tight recheck), re-invoke on the supervision cadence via the runtime's self-pacing mechanism; if no such mechanism is available, rely on completing-shipper re-invocation plus a manual re-run. **Never** stop while any item is unmerged and unblocked. When **every** item is `merged` or terminally `blocked`: run the **Closeout** (below), emit the `FLEET —` block, and do **not** re-arm.

## Supervision playbook (the heart of it)

For each in-flight agent, classify and act:

**Escalation-class outcomes → a fresh agent, never the same one.** A shipper whose reported terminal outcome is `verify-loop-halt`, or a **no-progress stop** (its build chain halted on its own progress guard — the same phase named twice with no artifact progress, reported as no forward progress), has an **escalation-class outcome**. No playbook ever continues such an item in the same agent: B never resumes it, D never nudges it, and no `SendMessage` is sent to its agent id. The report is itself conclusive terminal evidence, so the item enters C's parent-owned recovery gate directly — Boundary 2, the execution-shape-specific `postAttempt`, Boundary 3 — with no probe. On `disposition: retry`, dispatch a **fresh** replacement agent on the exact resolver-returned selection, which sees only the persisted artifacts and the ledger, never the failed transcript; when `retry.nextTier` is null (the item already runs on the top available tier) pass the returned selection unchanged and keep that tier. When the resolver instead stops the item as `exhausted` — including an item whose one-tier step-down (§"Model selection") already spent its one retry — block the item as `exhausted`: no fresh-agent retry is dispatched and the same agent is never continued. An item whose outcome is neither escalation-class nor a stall on progress triggers no escalation; A still governs it.

**Awaiting review → OBSERVE handles it, no playbook applies.** A row in `awaiting-review` is waiting on this orchestrator's deadline, not stalled: it is never probed, recycled, resumed as interrupted, or escalated for waiting, however long the deadline is. OBSERVE §"Review wait" sends its one continuation; only if that continuation cannot reach the agent does §C apply.

**Review-boundary hand-back → OBSERVE handles it, no playbook applies.** A shipper that reported `SHIP — Handed-off` with `Built: stopped at review boundary` (or `RUN — handed-off`) is waiting on **this orchestrator**, not stalled and not terminal: it is never probed, recycled, resumed as interrupted, or escalated for that report. OBSERVE §"Review boundary" runs its lenses and sends the one continuation message; only if that continuation cannot reach the agent does §C apply.

**A. Making progress → leave it alone.** A new commit, a dirty working state, or an updated pull request since last tick. Never recycle an agent whose worktree changed — that is work in flight (**dirty-status-is-not-a-stall**).

**B. Interrupted (API error / session limit / model limit / stream stall) → resume from transcript.** The completion notification shows the agent stopped with a partial result. Its work is durable if committed (**commit-early-push-often** is what makes it so). `SendMessage` the same `agentId`: "you were interrupted, nothing is lost — continue from your last step; commit and push what exists now." A limit that has since reset just needs the resume. B never applies to an escalation-class outcome: an agent that reported `verify-loop-halt` or a no-progress stop is not interrupted but terminal, so it is not resumed — route it through the escalation-class rule above.

**C. Suspected stall → probe once, then evaluate and replace only after terminal proof and resolver authorization.** When the runtime shows no child activity across TWO consecutive ticks and the delivery reads show **no** branch/pull-request artifact, silence still proves neither a clean tree nor a dead activation. Preserve the activation and `SendMessage` the same agent id once under the retained routing decision: "No artifacts are visible yet. Skip remaining setup and start `/wf:ship <ID>` now; report either active work or a terminal blocker." Do not `TaskStop` on elapsed silence or on the absence of an explicit dirty working-state checkpoint. Continue bounded supervision; while the probe lacks an explicit terminal/idle child response or a conclusive documented runtime terminal state, keep the activation, set its nonterminal scoreboard state to `awaiting-confirmation`, and re-arm supervision — never mark it `blocked` or enter closeout while the child may still run. Only after conclusive terminal evidence may the item become `blocked`, with the exact terminal reason recorded, or proceed through parent-owned recovery. An escalation-class report (above) is that conclusive evidence already: skip the probe and record it directly as the unit's terminal evaluation.

If that probed child explicitly returns a terminal zero-artifact/insufficient result, or the runtime provides a conclusive documented terminal state, record that unit's terminal evaluation. For an `isolated` prior this completes the retained attempt. For a `bounded-parallel` prior, keep the retained wave live and do not submit `postAttempt` until **every launched sibling** has its own conclusive terminal/success outcome; still-running siblings remain `in-flight`, unknown siblings remain `awaiting-confirmation`, both keep their pool capacity, and neither may be stopped or inferred. Only terminal/idle failed activations may be `TaskStop`ped. **Boundary 2 — before `postAttempt`:** atomically persist every terminal outcome and the complete ordered evaluation in the routing ledger before calling `resolve_routing` with `workspaceRoot` and `postAttempt`; after interruption, submit that retained operation without reinitializing the route or changing its attempt/provenance. Then the parent evaluates recovery according to execution shape:

- **`isolated` singleton:** submit top-level `sufficient: false` and `signals: ["repeated-failure"]`; omit `postAttempt.units` because unit evaluations are valid only for a bounded-parallel prior.
- **Top tier unavailable (only when the item's recorded routing `source` is `shipped-default`):** when the host rejects the spawn, or the child terminates, **because the host cannot run the requested model**, report `model-unavailable` in place of `repeated-failure` — top-level for an `isolated` singleton, on each such unit's entry for a `bounded-parallel` wave, while every sibling that failed for any other reason keeps its own `repeated-failure` in the same evaluation. A mixed wave is valid: the resolver steps the **whole** retry down one tier, so every failed unit is re-dispatched on a tier the host can run. Report it only on that explicit failure. A masked or mismatched `actualModel` is never itself a reason to submit it; log it instead (§"Model selection"). The resolver answers with a `retry` whose `retry.escalation` is `lower-stable-tier` and whose `retry.nextTier` is exactly one tier below the failed one; dispatch the fresh replacement on that returned model like any other retry. The step-down spends the item's one retry, so a second `model-unavailable` (or any later failure of that item) returns `exhausted` — surface it and block the item. An item whose recorded `source` is anything else (`invocation` from a `--model` pin, `project`, or `host`) never submits this signal and keeps `repeated-failure`; the resolver steps down only a delivered `shipped-default` selection.
- **`bounded-parallel` wave:** evaluate the **complete retained launch wave** before replacement. `postAttempt.units` covers exactly the unit ids actually executed under that retained decision, each once; ready items left queued outside that decision are not included; successful launched siblings are `sufficient` with no insufficiency signals, and only failed launched items carry `repeated-failure`. Top-level `sufficient` is false and top-level `signals` may remain empty because the insufficient unit entries carry the evidence.

Submit that shape-valid `postAttempt` with the retained decision, including its exact ordered `unitIds`. On `status: stop`, non-null `diagnostic`, or `retain`, dispatch nothing and surface/block exactly as returned. Every authorized replacement must dispatch a **fresh** agent. **Boundary 3 — before replacement spawn:** atomically persist the complete returned decision, including disposition, retry unit ids, retained unit ids, next attempt, selector provenance, basis, and escalation origin, before writing replacement activation intents or spawning anything. On interruption, resume only that persisted replacement operation; never rerun `postAttempt`, reset the retry cap, or create a fresh initial route. On `disposition: retry`, map the canonical resolver-returned `retry.unitIds` through the retained token→item-id map and dispatch replacements solely for those mapped items, in retained decision order: one id for an isolated singleton, or the insufficient subset for a bounded-parallel wave. An empty list dispatches nothing. **Before any of those replacements is spawned**, for each mapped item whose terminal outcome is `verify-loop-halt`, run §"The attempt-qualified persistence trigger" first. Obey the resolver-authorized retry shape (including composite-to-atomic when one bounded unit remains), and pass only the exact resolver-returned next-tier model/effort — never the original `invocationModel`, never an arbitrary caller shape/model change, and never the resumed same agent as the routed retry. A null `retry.nextTier` is not a missing value: the resolver deliberately made no tier change, so pass its returned selection exactly as returned and change nothing yourself. Retain successful units and restore dependency/input order after a selective bounded retry. **Before recycling, always confirm the agent's ACTUAL worktree from the runtime's live agent state** — an agent that migrated off its assigned path looks stalled but isn't.

**D. Mechanical-tail stall → continue once, then use the same parent-owned retry gate.** Work is committed and clean but the agent idles before the pull request / merge. When the item's reported outcome is escalation-class (`verify-loop-halt` or a no-progress stop), however much it looks like a tail stall, skip the continuation below entirely — send no `SendMessage` and go straight to the parent-owned gate per the escalation-class rule above. Otherwise, first `SendMessage` the same id to run its finalize step now; this is continuation under the retained routing record, so it makes no new routing call and changes no selector. If the child is truly dead or returns terminal insufficiency, `TaskStop` it and submit the same execution-shape-specific `postAttempt` described in C: top-level `repeated-failure` with no units for an isolated singleton; or complete executed-wave unit evaluations for bounded-parallel, with queued excess excluded. Obey stop/diagnostic/retain without dispatch. When and only when the returned disposition is `retry`, validate and map each canonical `retry.unitIds` token through the retained token→item-id map; for any mapped item whose terminal outcome is `verify-loop-halt`, run §"The attempt-qualified persistence trigger" first exactly as in C. Then spawn fresh replacement agents (per §"The shipper dispatch template") solely for those mapped item ids (the retained singleton item or bounded insufficient subset); a missing, ambiguous, stale, or duplicate mapping dispatches nothing and blocks with the mapping diagnostic. Always dispatch with the exact resolver-returned next-tier model/effort, or with its returned selection unchanged when `retry.nextTier` is null. Committed work is durable on the branch and `/wf:ship` resumes detect-first; successful siblings are never rerun. Take over only when the item is genuinely done bar the delivery tail.

**Two discipline rules that cost real rework:**

- **Never merge a pull request an agent is actively rebasing.** If the checks look clean but the agent is mid-sync, let it finish — merging out from under it lands a stale version and forces a corrective pull request. Only take over a merge when the agent has stopped.
- **Never touch a worktree an agent owns** (the **never-touch-a-worktree-an-agent-owns** rule). If the runtime shows a shipper on the shared checkout (a worktree-loss fallback), observation there is READ-ONLY until it merges and restores.

## The main-checkout hazard (know it cold)

A shipper's isolated worktree can vanish mid-run; a poorly-guarded fallback lands it on the **shared checkout**, on its feature branch. Symptom: the runtime shows the shared checkout on a feature branch carrying the agent's uncommitted work. When this happens: (1) do **not** run any write operation against the shared checkout; (2) observe it read-only; (3) let the agent finish and restore the trunk, or take over the tail by re-arming per playbook **D**; (4) confirm the shared checkout is back on the trunk afterward. The dispatch template's "STOP and report if your worktree is unavailable" rule is what prevents this — keep it in every prompt.

## Denied-call recovery — applies to YOU, the orchestrator

The run is unattended: a permission prompt that nobody answers is a dead fleet. The shippers get this rule in their dispatch prompt; **hold yourself to the same one.**

- **Shape calls to never prompt in the first place.** Stay inside the auto-approved grammar: one un-chained shell command per call, dedicated tools over shell (`Read`/`Glob`/`Grep`/`Write`/`Edit`), long bodies via a Written file.
- **If a call is denied anyway: it was shaped wrong.** Split the chain, move content to Write/Edit + file reference, use built-in filters, swap for an ungated equivalent. Never retry verbatim, never wait.
- **If two rewrites still get denied**, the action is genuinely gated: route around it (collect the leftover for the user instead), or mark the affected item `blocked` with the exact call in the notes — and keep the rest of the fleet ticking. One gated action must never freeze the loop.

## Model selection

The shipper model is set per dispatch via the Agent tool's `model` field. The **orchestrator** (you) always stays on the caller's model.

- **`--model <name>` given → pinned.** Every shipper uses that model; no per-item judgment. Practical use: `--model sonnet` to ship on a cheaper tier when low on tokens — the supervision logic is unchanged, though a cheaper tier may stall more often and lean harder on recycle/takeover.
- **`--model` omitted → the resolver decides.** `shipper` holds a static top-tier default in the resolver, so an unpinned item resolves to the top tier with `source: shipped-default`. Do **not** form a model opinion of your own and hand it over: that is the caller pinning a value the resolver was then asked to agree with, and it makes the routing ledger read `invocation` for a choice the resolver made. Instead, **as each item enters the ready frontier**, call `resolve_routing` for that item alone, reusing the Prerequisites `workspaceRoot` and passing `workspaceRoot` explicitly, with `role: "shipper"`, a singleton `unitIds` holding that item's canonical identity token, `supportsModelSelector: true`, `supportsEffortSelector: false`, and the fixed singleton shape evidence `{ workSurface: "external-context", atomicity: "atomic", unitCount: 1, unitsIndependent: false, ambiguity: "material", risk: "elevated", toolWork: "material", validation: "judgment", contextIsolation: "required", independentReview: false, returnContract: "mechanically-judgeable", requestedParallelism: 1 }`. The static default ignores shape evidence, so do not read the item's spec or merge terrain to build it. Hold the returned `model.value` and its `source` as that item's resolved selection, and persist both in that item's scoreboard row so the selection survives a `/clear` or a resume without a second call.

  - **Nothing is carried.** The item-level selection is a static default, not a resolver-derived one, so it never travels through `carriedModel` — the resolver refuses a carried `shipper` selection as a forged provenance claim, stopping the wave. The wave decision re-resolves the same default from the same configuration and records its own real source.
  - **A `null` `model.value` is a stated outcome, not a licence to improvise.** A higher-precedence layer (for example a host that exposes no model selector) may leave the selector unset. Record `unresolved: resolver returned no model — shippers run on the inherited model` in that item's row, warn once, and dispatch with **no** model selector so the shipper inherits. Do not substitute a judgment of your own: an inherited model that is visible in the row is honest, and a guess that looks like a resolved selection is not.
  - **Exactly one such call per item, for the whole run.** It is made once, on the item's **first** entry to the ready frontier, persisted in its scoreboard row, and thereafter **read back** rather than re-issued — so an item that stays queued across many ticks, is re-partitioned into a later wave, or is retried still costs one call, and a resumed run reconstructs the selection from the row instead of resolving again. The bound is on **this** item-level resolution: it does not count the wave decision, nor the routing each dispatched shipper performs on its own sibling edges inside its own context, which this skill neither makes nor pays for. Within that scope the cost is linear in item count with no per-item multiplier; anything needing a second item-level call for the same item is a scope escalation to raise, not an implementation detail.
  - **A host without the top tier degrades once, never fails the item for it.** When the top-tier dispatch genuinely fails because the host cannot run that model, and only when the item's recorded `source` is `shipped-default`, submit the parent-owned `postAttempt` with `signals: ["model-unavailable"]` (Supervision playbook §C) and dispatch the fresh replacement on the exact one-tier-lower model the resolver returns. It is bounded to one step per item — it spends the item's one retry.
  - **`--model` still outranks the default.** A pin travels as `invocationModel`, outranks the static default, and is never stepped down.
  - **A mismatch is logged, never retried.** When a completed shipper's reported `actualModel` maps to a different tier than the `model.value` it was dispatched on, append `model mismatch: requested <model.value>, ran <actualModel>` to that item's scoreboard row. Also write the line to the compact operational record, then carry on. The mismatch itself never triggers `postAttempt` or a replacement.
  - **Rows from an earlier release are re-resolved, not read back.** A resumed run may hold a `shipper` scoreboard row, or a retained routing prior, whose recorded source is `complexity-derived`. That provenance came from a release that derived the shipper model, and the resolver now refuses it. Resolve that item once afresh per the item-level call above, and overwrite the row. For a still-retained prior, never submit `postAttempt` against it: after the recovery playbook proves the item's activation terminal, route that item fresh as a first attempt only when the retained prior's `attempt` is `1`. A retained prior at `attempt: 2` or later has already spent the item's one retry, so block the item as `exhausted` instead of re-routing it. This is the one exception to the no-fresh-initial-route rule, and it applies only to this legacy provenance.
- Once that item's wave decision has been made, record that decision's source in the same row. A same-transcript continuation retains the original routing record without changing selectors. A fresh replacement uses only the exact model/effort returned by the parent-owned `postAttempt` decision for that unit; never choose an upgrade independently.

## Edge Cases

- **No delivery provider registered:** hard stop at Prerequisites (`FLEET — Blocked`) naming the missing surface — no shipper dispatched, nothing merged. The currency check has already run provider-less by then, so the block still carries `Currency: provider-less — …`; that is a **stated non-check**, never a pass.
- **The currency check cannot complete:** the read returns `<read-performed>` = false, or no version declaration is configured, or the running version is `unknown` → `Currency: not checked — <reason>` and the run proceeds unchanged. A degraded read is never presented as a performed check that found the install current, and the check never blocks, gates, or delays a dispatch.
- **Registered-but-unrecoverable delivery provider:** Prerequisites stops with the hedged candidate-naming diagnosis from the record's diagnostics, never asserting a pack owns the surface.
- **An item's model cannot be resolved:** the item-level call returns no model — a higher-precedence layer (for example a host that exposes no model selector) left the selector unset. The item is recorded `unresolved: resolver returned no model — shippers run on the inherited model` in its row and warned once; its wave dispatches with **no** model selector, so its shippers inherit the orchestrator's model. This is a stated degradation, never a licence to substitute a judgment of your own, and never a reason to stop the run.
- **The resolver rejects the routing call outright:** an error envelope instead of a decision — for example an input the running resolver does not recognise. There is no `status` and no `diagnostic` to read, so it is handled exactly like a stop: dispatch none of that wave, surface the rejection verbatim, and never retry it unchanged.
- **Umbrella given but no tracker registered:** an umbrella cannot expand tracker-free → stop and ask for an explicit id list plus `--after` edges.
- **A blocker ends `blocked`, not `merged`:** its dependents can never become ready — mark them `blocked (upstream)` and surface it; don't spin.
- **Cyclic or missing dependency:** if the graph has a cycle or an edge to an unknown id, stop and report it before dispatching anything — never guess an order.
- **Same-file collision slips through (not serialized):** the losing agent hits a content conflict at merge. Let it rebase-and-resolve; if it can't autonomously, take over the rebase or serialize the remainder.
- **All shippers idle but nothing ready:** every unmerged item is blocked by an unmerged item that itself is blocked → deadlock or an unfinished blocker; report the frontier and stop re-arming if truly deadlocked.
- **`/wf:ship` absent in a shipper:** it falls back to the gated-loop pipeline (`/wf:run` loop → `/wf:pr` → `/wf:tf`); if neither exists, it reports and stops — `/wf:fleet` orchestrates shippers, it does not reimplement them.
- **An item's ceremony cannot be proven:** the receipt read returned a status other than `ok` (including `foreign-root`, when the row's recorded worktree is not provably a worktree of this repository's family, or no longer exists), the row records no worktree, a required subject is missing, a record fell outside the run's receipt window, the route was undecidable, or a record came back `unmatched` — including the case where a shipper wrote a receipt-shaped file itself, which the resolver refuses to admit, and a record edited after issue, which fails its seal. The item is recorded **unproven** with that mechanical reason in its row's `notes`, counted in the `Ceremony:` tally and the tick REPORT line, and never logged as a clean run. A well-formed reported block changes none of this — it was never the evidence. The merge stands (it cannot be undone), and the item's possibly-skipped gates are flagged for a follow-up pass. The cause is never asserted.
- **A whole run reports zero proven:** three conditions each produce this. **(a)** The shippers' worktrees were unreachable at the proof-of-ceremony check — no row recorded a worktree, or every recorded worktree was already gone or outside this repository's family — so every read was `foreign-root` or never issued. Receipt verifiability is keyed on the worktree that issued the receipt; the family read reaches a shipper's worktree only while it exists, and nothing imports its evidence after removal. **(b)** A resolver runtime older than the family read does not expose `read_family_run_evidence` at all, so the query cannot be issued — an older runtime's own-root `read_run_evidence` is **not** a substitute, because under the isolated-worktree dispatch mandated here it can only return `absent`. **(c)** A resumed scoreboard predating the `**Opened:**` stamp has no receipt window. In every case **every affected item is legitimately unproven**, and the block says so in explicit zeros. That is the check failing closed — proving nothing rather than assuming everything — and it is **never** remedied by widening the match, reading a root the row does not record, dropping the window, or falling back to the reported block. Condition (a) or (b) means the tally did **not** establish anything about those items, and it must be read as "not established" rather than as evidence against any of them. Say so, naming the condition, when reporting the run.
- **An item's task artifacts cannot be persisted:** its worktree was unreadable or already gone when the persistence step ran, the source was refused (it resolved outside the recorded worktree, or onto this orchestrator's own workspace), or the write failed part-way. The item is recorded `not-persisted: <the mechanical reason>` in its row's `notes`, counted in the `Persistence:` tally and the tick REPORT line, and named among the not-persisted ids — never left as an item that silently has no artifacts. The failure is confined to that item: every other terminal item still persists. Because the set is staged and moved only when complete, a part-way write leaves no half-populated folder behind. Nothing is retried against a path the row did not record, no worktree is touched to recover it, and the cause is never asserted.
- **An item never had a worktree at all:** an item blocked before it was ever dispatched has no recorded worktree and therefore no set to persist. It is recorded `no-artifacts:` and counted apart from the failures — reported, but never as an incomplete process record, because nothing is missing. Forcing it into the not-persisted count would assert a cause the step is forbidden from asserting and would manufacture a gap that does not exist.
- **The destination already holds a task folder for that id:** a local run, an earlier fleet run, or a re-ship can leave one there. The persisted set is written beside it and neither copy is deleted, so an existing folder is never clobbered and the operator keeps both to compare.
- **A whole run persists nothing:** the block reports `0 persisted`, and **which** of the other two counts carries it decides what that means. A non-zero not-persisted count is the loud failure — the run's process record is incomplete and says so, rather than letting an absent artifact set read as an item that never produced one. A run whose terminal items are all `no-artifacts` also persists nothing, but its not-persisted count is zero and its record is **not** incomplete: nothing was missing, so claiming incompleteness there would be a false alarm in the opposite direction.
- **A scoreboard written before this step existed:** its rows carry no persistence state at all. Those items are recorded `no-artifacts:` with that stated reason and are never back-filled, so an older run is neither re-persisted from worktrees that have since gone nor reported as an incomplete record for a feature it predates — the same degradation the ceremony check applies to a scoreboard with no receipt window.
- **Undeleted remote branches / un-swept worktrees:** merged branches and clean worktrees often survive (destructive version control is barred) — closeout lists them from the scoreboard for one manual sweep by the user, never a raw query.
- **A requested review is still outstanding:** the shipper hands back `Built: awaiting review` and the row waits in `awaiting-review` against the deadline OBSERVE §"Review wait" recorded; one continuation with `--review-lapsed` follows the deadline, whether the wake fires once, twice, or not at all. A review that never lands stops the item `blocked` with its open pull request — never a merge. With `Review Wait Minutes` at `0`, or in a runtime with no self-paced wake (headless print mode is unsupported for the wait), the item is recorded `blocked: review not awaited — <reason>` instead of waiting — never a hang and never a pass.
- **Mid-run interruption:** re-invoking `/wf:fleet` with no arguments resumes from `_local/fleet/scoreboard.md`; every `awaiting-review` row's deadline is read back from its `notes`, never re-stamped.

Currency:         <current | trailing (running <v>, published <v>) | provider-less | not checked — <reason>>

`Version:` is the run-scoped resolved version held at Prerequisites — the harness this run executed. It renders on **every** pass, and `unknown` when the resolver could not determine it; it is never omitted.

`Currency:` is the outcome of the Prerequisites currency check, in that step's grammar, rendered verbatim on **every** pass — including a `Blocked` one. Only `current` says the harness is not behind, and only a performed read can produce it: `provider-less` and `not checked` name what did **not** happen and are never rounded up to a pass here.

**Adding a slot to this block?** Follow the shared pipeline conventions doc (`resolve_content({ workspaceRoot, ... })`, `class: shared`, `ref: pipeline-conventions.md`) §"Run-block slot convention" — never a raw `Read` of the plugin-cache path: append the slot immediately above `Next:`, pad its value to this block's column 19, and always render it with a stated fallback token.

`Ceremony:` is the proof-of-ceremony tally from OBSERVE, rendered verbatim on **every** pass. It always states all three counts and omits none: a run in which nothing could be proven reports `0 proven (0 artifact-backed, 0 invocation-only)` alongside a non-zero unproven count — an explicit zero, rather than the silence an auditor would read as a clean run. `<a>` and `<i>` are **item** counts that partition `<p>` exactly, so `<p>` equals `<a>` plus `<i>`; the split is always rendered rather than the total alone, because `invocation-only` is the weaker attestation and has to stay readable as itself. `<p>` and `<u>` together account for every item that reached a terminal outcome. `unproven: none` is the stated fallback when every item is proven.

`Persistence:` is the task-artifact persistence tally from OBSERVE, rendered verbatim on **every** pass. `<k>`, `<n>` and `<x>` are **item** counts — the same three tokens step 4 settles into the rows, so tally and rows reconcile by construction — and they are rendered **against `<t>`, the number of items that have reached a terminal outcome**, so an item deferred because its activation is still live is visible as the shortfall rather than vanishing from the denominator. That denominator is the point: the sibling ceremony check bans a terminal item silently dropping out of its tally, and reporting the evaluated subset alone would reintroduce exactly that. A run that persisted nothing reports an explicit `0 persisted` rather than the silence an auditor would read as a complete process record. `not-persisted: none` is the stated fallback when no terminal item failed. **Only `<n>` carries the incomplete-record signal:** a non-zero `<n>` means the run's process record is missing something it should have, and the named ids are where. `<x>` is reported apart from it precisely because those items never had a set to persist, and counting them as failures would manufacture a gap that does not exist.

`Review sweep:` is the aggregate outcome of the `fleet.closeout-review` composition point, rendered on **every** pass. When the slot fired, it carries the summed tally across every merged row swept — `<sf>` candidates judged, with every candidate disposition inside it — `<sm>` survived verification against the swept pull request's merged ref (the `merged-ref-read` export, never the orchestrator's checkout), `<sk>` were verified-invalid, `<sj>` moot and `<sv>` unverifiable, plus two counts sit apart from that sum: `<sa>` for rows that produced nothing to judge, and `<sn>` for items the sweep never judged at all, each with a stated reason — past the served body's ingest cap or its candidate cap, or the distiller returned no block for it. **`<sa>` is itself split**, because its reasons are not equally clean: `<sq>` counts rows with a genuinely empty review at read time — an honest zero — while `<sr>` counts rows whose read, probe or reachability check **could not run at all**. A non-zero `<sr>` is reported the way a non-zero `<sn>` is: those rows were not verified, and a run that collapsed them into one number would let a fleet in which every review read failed render beside a healthy-looking sweep line — a non-zero `<sn>` means the sweep was **incomplete**, which the line must show rather than let a healthy tally imply completeness. **`<sm>` counts survivors, not tracker writes:** a survivor that could not be filed still counts there, so `filed:` and `unfiled:` are rendered as two separate values and never inferred from `<sm>`. **The `Review sweep:` placeholders are deliberately `s`-prefixed** — the count placeholders on the `Ceremony:`, `Persistence:` and `Currency:` lines already bind `<a>`, `<u>`, `<k>`, `<n>`, `<t>`, `<x>`, `<p>`, `<i>` and `<v>`, and reusing them here would give one token two meanings inside one fenced block that downstream skills grep. **The line's two reason channels are prefixed for the same reason** — `<sn-reasons>` says why items went unjudged, `<sx-reasons>` says why survivors went unfiled, and one shared `<reasons>` token would have carried both meanings on a single line. (That claim is about the tokens this addition introduces; the block's *pre-existing* reuse of `<n>` and `<k>` on its `Scope:` and `Next:` lines predates it and is not something the prefixing fixes.) `filed: <issue-ids | none>` carries the **tracker issue** ids it wrote — deliberately not the bare `<ids>` this block already binds to fleet item ids on the `Ceremony:` and `Persistence:` lines — with `filed: none` the stated fallback when nothing was written to a tracker, and `unfiled: <sx> — <sx-reasons>` names how many survivors were not written and why (a stated reason per survivor — commonly no tracker registered, no filing parent resolved, filing cap reached, filing failed, not filed — dry run, or already filed on an earlier run), with each one's full evidence reported above the block. **That channel is load-bearing on the tracker-free path**, where no filing parent exists and therefore *every* survivor is unfiled — a block with nowhere to say so would discard the whole run's findings while rendering a healthy-looking count. **`not attempted` is the stated fallback token** for every other case: the slot was unfilled, unresolved, or refused, or Closeout has not reached that point yet on this pass. `not attempted` is never rendered as a zero tally and a zero tally is never rendered as `not attempted` — a sweep that ran and found nothing is a different fact from no sweep, and the line that conflated them would recreate the silent-finding gap this point exists to close.

`Lenses:` is the per-item lens-coverage figure from OBSERVE, rendered on **every** pass: one entry per terminal item OBSERVE has read — an item whose activation is still live has no entry yet, never an `unknown` one — in scoreboard order, each the item's own `04_verify.md` `**Lenses:**` value verbatim — `<lc>` of `<le>` expected `verify` lens contributors completed, and `<li>` run inline by the verifying agent rather than independently (counted as expected, never as completed) — or `unknown — <reason>` when that value could not be read. `0/0 completed, 0 inline` is an explicit zero for an item whose project registers no lens contributor, never an omitted entry. A count short of expected carries verify's ` — incomplete: <role>, …` suffix verbatim, so a lens that failed or stalled at the review boundary is named per item and never reads as full. `none — no terminal item read` is the stated fallback while no terminal item has been read — nothing has reached a terminal outcome yet, or every terminal item's activation is still live. **The placeholders are deliberately `l`-prefixed** because `<i>` is already bound on the `Ceremony:` line, the same collision rule the `Review sweep:` placeholders follow. The figure is reporting only and gates nothing; the same value is echoed at the tail of the tick REPORT line under the `lenses:` label.

`In flight:` is the lossless active-activation projection, despite its retained label: include every `dispatched`, `in-flight`, `awaiting-confirmation`, and `awaiting-review` scoreboard row with its state tag. A row without a persisted `agentId` is still listed by `activationIntent`; never omit it or collapse it into `Waiting on deps:`.

`Complete` — every item is a merged pull request. `Blocked` — a required condition failed (no delivery provider, a cyclic graph, an umbrella with no tracker, or a deadlocked frontier); the `Next:` line names the command that clears it (`/wf:ship <id>` to retry one item, `/wf:charter` to re-decompose, or `/wf:init` for missing config). `Running`/`Waiting` — the loop re-arms.

**The final-output block must always be the very last thing output to chat.**
